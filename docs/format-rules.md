# Format rules

Rules for a rendered Version: `resume/versions/general.md`, the one stored base Version, and a tailored Version at `private/candidates/<folder>/version.md`, beside the Candidate's `job.md`. Layout (fonts, sizes, margins, spacing, single column) is fixed by `resume/scripts/resume.css`; the Version's shape is generated by `resume-version` from the Project files and checked by `resume-pdf`. Adopted from upstream `resume-formatter`, which is not installed.

- A Version is the Markdown twin of its PDF, every line the page shows, no frontmatter: `# name`, the title, the contact line, the summary, `## Skills`, `## Professional Experience`, `## Projects`. The sections carry `### [slug] Name – description` entries, each with a role row `Role | Dates` and `- [key] Bullet` lines; the renderer drops the `[slug]` and `[key]` prefixes. Every sourced line (name, contact line, headings, role rows, canonical Bullets) equals its source in the Profile; a Version is regenerated, never hand-edited.
- Sections, in order: summary, Skills, Professional Experience, Projects. The name, the title as the headline, the contact line and the summary carry no header. Skills holds the Plan's grouped lines; every term is a canonical Skill, spelled as the Project file's `keywords` spell it, abbreviation included when the name carries one (`Role-based access control (RBAC)`), never as a posting spells it. Professional Experience holds the Projects whose `employment` is not `independent`; Projects holds the rest, each in `resume_order`. No Education section. Header names come from the ATS-recognized set only.
- Summary: identity or title, years, key Skills, value; it names the title's role noun. No objective, no trait filler, no third person.
- Contact line, from `profile/profile.md` `contact`: location with UTC offset, email, GitHub, LinkedIn. No phone, no photo, no street address.
- Entry heading: `[Name](url) – description` and a role row `Role (Contract) | Mar 2019 – Present`, generated from the Project file's `name`, `url`, `naming`, `role`, `employment`, `start`, `end` and `description`. A Project named only when its Naming is `public`; an `nda` Project renders as "NDA client".
- Role suffix, by `employment`: `contract` adds ` (Contract)`, `freelance` adds ` (Freelance)`; `full-time`, `part-time` and `independent` add nothing.
- Dates: `Mon YYYY – Mon YYYY`, the English three-letter month, an en dash with a space each side; `Present` in place of the end month when the Project has no `end`. The generator formats `start` and `end` (`YYYY-MM`) this way. One format throughout a Version.
- Bullets: canonical Bullets from the Project files, verbatim, in Plan rank inside each Project, at most two rendered lines each. A tailored Version may carry a Variant under a canonical Bullet's key: it reorders and re-emphasises that Bullet, never adds a claim, every number and Keyword from the canonical Bullet. The general Version holds canonical Bullets only; a wording the canonical Bullet cannot back is a Bullet edit.
- Characters: no emoji; no symbols beyond `•`, `–` and `|`. Bold and italic sparingly.
- Sent PDF name: `Dolbilov_<Role>_<Company>_<MonYYYY>.pdf`, role as the posting's title in CamelCase, company as the Job's `company`, the month of the render, whichever Version it renders (general or tailored); `resume-pdf <Candidate folder>` writes it into the Candidate folder, the file that goes out. The tailored source is always `version.md`. The public general Version keeps `Konstantin_Dolbilov_Resume.pdf`.
